## 1. 要件整理(原文ベース)

| 項目 | 内容 |
|---|---|
| 概要 | Windows 11 ⇔ Ubuntu 26.04 でテキスト/画像/ファイルを共有。Deskflowのクリップボード機能代替+ホームラボ全体の共有基盤 |
| 通信方式 | NAS上のSMB共有フォルダ経由。専用サーバー不要 |
| 実装言語/GUI | Python + PySide6(希望) |
| 初期機能 | テキスト送信/画像送信(PNG)/ファイル送信/自動受信(ON/OFF)/手動受信 |
| GUI最低要件 | 共有フォルダ指定、現在の内容表示(テキスト or サムネイル)、送信/受信/履歴ボタン、自動受信チェックボックス |
| 対応データ(将来) | HTML/URL/フォルダ/その他クリップボード形式 |
| 履歴 | 最新20件程度、再コピー可能、将来検索機能 |
| 設定 | NAS共有フォルダ、自動受信ON/OFF、履歴件数、起動時常駐 |
| 設計方針 | GUI/バックエンド分離、保存方式抽象化、SQLite/REST API移行可能、モジュール化 |
| 対象外 | SQLite、REST API、AKM/HMS連携、OCR、AI検索、タグ、お気に入り |
| 補足 | 単なる同期でなく「一時的データ受け渡しハブ」。ChatGPT/Claude Code/両OS間でコード・ログ・スクショの受け渡しも視野 |

`CLAUDE.md`と要件ドラフトはおおむね整合しているが、ドラフトの方が具体的(Python+PySide6指定、履歴20件、起動時常駐など)。一方で`CLAUDE.md`にある以下2点はドラフト側に明記がなかった(→本レビューで補完済み、詳細は3章)。

- 同一クライアントが作成した項目は無視する
- 不完全ファイル読み込み防止のためのアトミック書き込み

## 2. サーバー側フォルダ構成(確定)

- 共有方式: SMB
- パス: `\\192.168.10.16\sharedclipboard`(Windows) / `/mnt/networkstorage/sharedclipboard`(Ubuntu)
- 既存フォルダ: `current / objects / history / temp / logs`(NAS側に作成済み)
- 存在しないフォルダはアプリ起動時に自動作成する(Phase 1のストレージ抽象層の要件とする)
- 保存層は将来SQLite移行できるよう抽象化する(`CLAUDE.md`の設計方針と一致)

**確定**: `current` はディレクトリとして運用する。初版では以下の構成のみ配置する。

```
SharedClipboard/
└── current/
    └── current.json
```

将来的に `current.lock` 等の一時ファイルを同ディレクトリに追加できるよう、`current`は最初からディレクトリとして設計する(`current.json`の一時ファイル置換もこのディレクトリ内で完結させる)。

**確定**: `logs` ディレクトリは将来拡張用の予約領域。初版ではNASへのログ集約は行わず、各クライアントのログはローカルにのみ保存する(ロギング先はプラットフォームごとの標準的なローカルログパスを想定し、Phase 0のロギング初期化で決定する)。

## 3. 初版仕様の決定事項

### 3.1 自動受信
- SMB共有を既定1秒間隔でポーリングする。
- ポーリング間隔は 0.5秒 / 1秒 / 2秒 / 5秒 から設定可能。
- NAS切断中は5秒、連続失敗時は最大30秒まで間隔を延長し、復旧後は設定値へ戻す(指数バックオフ的な劣化運転)。

### 3.2 履歴・オブジェクト保持
- GUI表示履歴: 最新20件。
- 実体ファイル(objects/history配下)は最大50件かつ合計2GBまで保持。
- いずれかの上限を超えたら、最新項目を除き古い順に削除。
- `temp` 内の24時間以上経過したファイルは起動時に削除する。

### 3.3 current.json スキーマ
フィールド: `schema_version, item_id, client_id, client_name, created_at_utc, type, mime_type, object_path, original_name, size_bytes, sha256, text_encoding`

- `item_id` は ULID または UUID を使用。
- グローバル連番 `seq` は初版では使用しない(本レビュー2章で提案した`seq`案は不採用)。
- 書き込み手順: 実データを `temp` へ書き込み → `objects` へリネーム → 最後に `current.json` を一時ファイルからアトミックに置換。
- 同時送信時は最後に書き込まれた `current.json` を「最新」とするが、各送信項目は個別に履歴へ残るため取りこぼしはない。

> **v1で許容するトレードオフ**: `seq`を使わないため、`created_at_utc`のみに依存すると端末間の時刻ズレが履歴の表示順に影響しうる。今回はNTP同期済みの前提で許容するが、順序ズレが実運用で問題になった場合はローカル受信時刻でのソートや`seq`導入を再検討する。

### 3.4 改行コード
- テキストクリップボードは UTF-8・LF に正規化して保存する。
- ファイルとして送信されたデータの文字コード・改行コードは変更しない(バイナリ同一性を保持)。

### 3.5 サイズ上限
- テキスト: 2MB
- 画像: 50MB
- 一般ファイル: 500MB
- 上限超過時は送信を拒否し、理由をGUIに表示する。
- ファイルI/OとSHA-256計算はバックグラウンドスレッドで実行し、GUIをブロックしない。

## 4. プラットフォーム固有リスク

1. **SMB越しのファイル監視不可** — 自動受信はポーリング前提で設計する(3.1で確定)。
2. **SMBのアトミックリネーム保証がOS/実装依存** — Windows SMBクライアントとLinux cifs/smbfsマウントで挙動検証が必要。`temp`→`objects`リネーム、`current.json`の一時ファイル置換の両方を両OSで実地テストする。
3. **クリップボードAPIの差異**(Windows: `pywin32`等 / Ubuntu: Wayland対応のQt Clipboard) — 画像フォーマット・HTML/URL将来対応時に差異が顕在化しやすい。

   実装(Phase 2)では、PySide6の`QClipboard`で両OS共通実装とした(Qt自身がWin32/X11/Waylandの差異を吸収するため)。Ubuntu 26.04(GNOME/Wayland)実機で検証した結果、**ウィンドウがフォーカスを持たない状態だと、GNOMEがクリップボードの実データを渡さず、ポータル経由の制限された情報(`application/vnd.portal.*`)しか取得できない**ことを確認した。実際にクリック可能なウィンドウを表示し、フォーカスした状態で読み取ると、テキスト/ファイルとも正しく検出できた。

   → **Phase 4(自動受信)への影響**: 自動受信はユーザー操作なしで定期的にローカルクリップボードへ書き込む想定だが、その瞬間にアプリのウィンドウがフォーカスされているとは限らない。Ubuntu/Waylandでは書き込み(`setText`/`setImage`/`setMimeData`)についても同様の制限を受ける可能性があるため、Phase 4実装時に実機で書き込み側も検証し、必要であれば書き込み直前に一時的にウィンドウを前面化/フォーカスするなどの対処を検討する。
4. **ファイル名の禁止文字・パス長制限の差異** — `object_path`はハッシュ/ULIDベースにして、OS依存文字を回避する。
5. **起動時常駐の実装方式の違い** — Windows(スタートアップ/レジストリRun/タスクスケジューラ)とUbuntu(systemd --user / XDG autostart)で完全に異なるため、プラットフォームアダプタ層で分離する。
6. **時刻同期への依存** — `created_at_utc`基準の順序表示・保持期限判定(temp 24時間ルール等)はNTP同期が前提。両機のNTP設定確認を運用手順に含める。

## 5. 実装計画(フェーズ分割)

| Phase | 内容 |
|---|---|
| 0. 足場作り | Pythonパッケージ構成、依存管理、ロギング初期化、`config/`読み込み |
| 1. ストレージ抽象層 | `StorageBackend`インターフェース定義→NAS実装。`current/objects/history/temp/logs`の起動時自動作成、`current/current.json`のスキーマ実装(3.3)、アトミック書き込み(objects側はtemp→objects、current.jsonは`current/`ディレクトリ内で一時ファイル置換)、破損メタデータへの耐性。単体テスト(中断書き込み・不正JSON) |
| 2. クリップボードアダプタ | プラットフォーム非依存インターフェース+Windows/Ubuntu実装をモック可能な形で分離 |
| 3. アプリケーション/サービス層 | 送受信オーケストレーション、`client_id`による自クライアント無視、サイズ上限チェック(3.5)、SHA-256計算のバックグラウンド化 |
| 4. 受信ロジック | 手動受信 + 自動受信(可変ポーリング間隔・バックオフ、3.1) |
| 5. 保持ポリシー実装 | 履歴20件/実体50件・2GB上限の削除ロジック(3.2)、temp掃除(起動時24時間ルール) |
| 6. GUI(PySide6) | フォルダ選択、現在の内容表示、送信/受信/履歴ボタン、自動受信チェックボックス+間隔選択。ロジックは呼び出すだけでGUIに業務ロジックを書かない |
| 7. 設定・常駐 | 設定永続化、OSごとの起動時常駐アダプタ |
| 8. パッケージング | Windows実行形式、Ubuntu用インストール手段(簡易インストールを優先度3としているため) |
| 9. 結合テスト・耐障害性 | NAS切断シミュレーション(バックオフ挙動含む)、中断書き込み、破損メタデータ、サイズ上限拒否、クロスプラットフォーム相互送受信の実機/VM検証 |

各フェーズはCLAUDE.mdの「小さくテスト可能なステップで実装」方針に沿って、Phase単位でPRを分けることを想定する。
